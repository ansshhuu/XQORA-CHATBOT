# XQORA Chatbot

AI customer support chatbot for theXQORA Technologies website. It answers questions about XQORA's services, recommends the right offering, collects leads, escalates complex queries to the team, and
collects feedback reducing manual support load and improving lead quality.

Built with FastAPI and a lightweight JavaScript widget, using a multi-agent
architecture: one orchestrator classifies intent and routes to a dedicated agent for
FAQs, recommendations, lead collection, escalation, or feedback.

## How it works

Every `/chat` request goes through a single decision point, `app/orchestrator.py`:

1. **Feedback check** — if the session was just asked for feedback, the reply is parsed
   for a rating/comment (see [Feedback](#feedback)) before anything else happens.
2. **Closing-phrase / natural-close check** — a sign-off ("thanks", "bye"), a just-finished
   lead submission, or an escalation all trigger a casual feedback ask.
3. **Lead-flow check** — if the session is mid-way through lead collection, the message is
   routed straight back into `lead_agent.py` instead of being reclassified.
4. **Guardrail + intent classification** — `intent_agent.py` runs deterministic pre-checks
   (near-empty input, greetings, bare category words like "pricing", self-identity
   questions, a hard off-topic keyword/pattern filter, a hard escalate-signal filter) before
   ever calling the AI classifier, then labels the message `faq`, `recommend`, `lead`,
   `escalate`, or `off_topic`.
5. **Specialist agent dispatch** — the matching agent (`faq_agent.py`, `recommend_agent.py`,
   `lead_agent.py`, or `escalation_agent.py`) generates the reply, grounded in
   `data/faq.json` / `data/services.json` where applicable.
6. **Logging** — the turn is saved to `ChatHistory` (skipped for greetings/off-topic
   refusals) so the next message's classification and specialist replies can use recent
   conversation context.

## Setup

```bash
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env          # fill in your Groq API key, OpenRouter API key (fallback), Resend key, team email, DATABASE_URL, and (optional) Google Sheets config
python -m app.database        # one-time: creates tables against DATABASE_URL (re-run whenever you point at a fresh DB)
uvicorn app.main:app --reload
```

Visit `http://127.0.0.1:8000` — should return a health check response.
Visit `http://127.0.0.1:8000/docs` for interactive API docs (auto-generated by FastAPI).

## Database

`DATABASE_URL` is required - there's no default, so the app fails fast at startup with a
clear error if it's unset. Any SQLAlchemy-compatible URL works:

- Local dev: `sqlite:///./xqora_chatbot.db` is fine.
- Production/Vercel: a real Postgres connection string (e.g. from Supabase or Neon's free
  tier) - Vercel's filesystem is ephemeral per invocation, so SQLite (a file on disk) isn't
  viable there.

Tables are created via `python -m app.database`, run once manually against whichever
database `DATABASE_URL` points at (see `app/database.py`'s `__main__` block) - not
automatically on every app startup. On serverless, the startup event fires on every cold
start, so auto-creating tables there would mean redundant (and, under concurrent cold
starts, racy) DDL against production on every cold start instead of a one-time setup step.

## The chat widget

`public/widget.js` is a single self-contained script — no external framework or CSS
library, so it works standalone when dropped into any page. It's the single source of
truth for the widget: Vercel serves everything under `public/` directly from its CDN at
the site root, bypassing the Python function entirely (see [Deployment](#deployment)) -
nothing in `app/main.py` mounts or serves it, so this only works when running through
Vercel (`vercel dev` locally, or a real deployment), not plain `uvicorn`.

**Drop-in usage** (on the real XQORA site, pointing at wherever the API is deployed):

```html
<script src="https://YOUR_API_HOST/widget.js" data-api-url="https://YOUR_API_HOST/chat"></script>
```

- `data-api-url` is optional. If omitted, the widget POSTs to `/chat` on the page's own
  origin — which is exactly what happens in local testing, since `public/test.html` is
  served from the same origin.
- To test locally: run `vercel dev` (see [Deployment](#deployment)), then visit
  `http://localhost:3000/test.html`. The bubble should appear fixed to the bottom-right
  corner; clicking it opens the panel.

**session_id behavior**: the widget generates one `session_id` per page load
(`crypto.randomUUID()`, with a fallback for older browsers) and keeps it in a JS variable
only — not `localStorage` or a cookie. Refreshing the page starts a new session. The
backend also accepts and honors a client-supplied `session_id` on `/chat`, so this is a
widget-side choice, not a backend constraint — swap in persistent storage in `widget.js`
later if cross-refresh continuity is wanted.

**Restyling**: all colors/radii/shadows live in the `THEME` object at the top of
`widget.js`:

| Key | Value | Used for |
|---|---|---|
| `teal` | `#14b8a6` | bubble background, user message bubbles, send button, input focus ring |
| `tealDark` | `#0d9488` | send button hover |
| `navy` | `#0a1e3f` | chat panel header background |
| `textDark` | `#0f172a` | bot message text |
| `panelBg` | `#f8fafc` | chat panel body background |
| `white` | `#ffffff` | header text, bubble icon, input background |
| `radius` / `radiusSm` | `14px` / `10px` | panel corners / message bubble & input corners |
| `shadow` / `bubbleShadow` | — | panel drop shadow / bubble glow |

Nothing else in the file needs to change to reskin the widget — markup, layout, and the
`/chat` wiring are independent of `THEME`.

## CORS

`CORS_ORIGINS` in `.env` controls which origins may call `/chat` from a browser (the
widget relies on this). **The default in `app/core/config.py` is a placeholder**
(`https://xqora.com,https://www.xqora.com`) — replace it with the real production
domain(s) before deploying:

```
CORS_ORIGINS=https://xqora.com,https://www.xqora.com
```

Comma-separated for multiple domains (e.g. staging + production). Never set this to `*`
in production — that would let any website embed the widget and call this API.

## Feedback

After a conversation reaches a natural close point — a lead gets submitted, an escalation
happens, or the user signs off with something like "thanks" or "bye" — `feedback_agent.py`
casually asks for a quick rating/comment (e.g. "Before you go, how'd this chat go? (1-5,
or just tell me)"). This only fires once per session:

- A reply starting with a number 1-5, or containing a recognized rating word (e.g.
  "great", "poor"), is saved to the `Feedback` table (`session_id`, `rating`, `comments`,
  `date`) and the session is marked as given.
- Anything else — ignored, or the user just moves on to another question — marks the
  session as declined. The ask is never repeated, and the message that declined it is
  still processed normally (not swallowed).
- Detection is deterministic (regex/keyword-based), not AI-based, so a feedback reply can
  never be misclassified as off-topic or misrouted to another agent.

## Lead capture, persistence & isolation

`lead_agent.py` collects a lead's details (name, company, email, phone, a short need
description) step by step across turns, tracked per `session_id`.

**Session persistence**: in-progress collection state is cached in memory for
same-process speed, but that cache is not the source of truth - every turn that changes
the state also saves it to the `lead_sessions` table (`app/database.py`), and a cache miss
(a session's first message, or any session that predates the current process - e.g. right
after a restart) reads it back from there instead of starting the form over. That's what
lets a partially-filled form survive a server restart: the next message after a restart is
recognized as still mid-collection and resumes from the field it was paused on, with
everything collected so far intact. Abandoned in-progress forms are cleared out of
`lead_sessions` on the same TTL (`SESSION_TTL_SECONDS`) as the in-memory cache. A
multi-worker/multi-instance deployment would still want a shared cache (e.g. Redis) in
front of the DB to avoid a DB round-trip on every turn, but correctness no longer depends
on the in-memory dict surviving.

**Session isolation**: all session state (in-progress lead data, the completed-lead reuse
cache, feedback ask/response state) is looked up strictly by `session_id` - dicts keyed by
`session_id` in memory, and the `session_id` primary key on `lead_sessions` in the DB -
never a shared/global variable, so two concurrent users' sessions can't see or overwrite
each other's data. `tests/test_e2e.py --mocked` includes a dedicated regression
(`_feature_session_isolation_concurrent_leads`) that interleaves two lead flows turn by
turn under different `session_id`s and confirms neither the in-memory state nor the
persisted `lead_sessions` rows cross over, plus `_feature_lead_session_db_persistence`
which simulates a restart (clearing the in-memory cache mid-flow) and confirms the form
resumes correctly from the DB.

On completion, the lead is saved to the `Leads` table and forwarded to the team inline,
synchronously, before `handle_lead_message` returns (`lead_agent._forward_lead_now`): an
email through Resend (`lead_service.py`), and a new row in a shared Google Sheet
(`sheets_service.py`, see below). This used to be a FastAPI `BackgroundTasks` job run after
the response was sent, but that pattern is unreliable on a serverless platform (Vercel) -
the function can be frozen or torn down before a deferred task runs, so the email could
silently never send. Both calls already block with their own bounded timeout (10s), so
running them inline just moves that already-bounded latency into the request instead of
after it - a deliberate tradeoff of a few hundred ms of response time for guaranteed
delivery. The two are independent - each is wrapped in its own try/except, so a Sheets
failure never blocks or breaks the email (or the lead already saved to the DB), and vice
versa.

## Google Sheets integration

Every completed lead is appended as a new row (name, company, email, phone, requirement,
timestamp) to a shared Google Sheet, via a service account - no per-user OAuth flow, no
browser consent screen, just server-to-server auth. This runs inline in the same call as
the email forward (see above), before the chat response is sent: a failure (missing config,
network error, bad credentials, wrong sheet ID) is logged server-side only, never surfaced
to the user, and never affects the email forward or the lead record itself.

**Setup**:

1. In the [Google Cloud Console](https://console.cloud.google.com/), create or select a
   project, then enable the **Google Sheets API** for it (APIs & Services -> Library).
2. Create a service account (APIs & Services -> Credentials -> Create Credentials ->
   Service Account). Give it any name; no special roles are needed.
3. Open the service account, go to the **Keys** tab, and create a new JSON key. This
   downloads a `.json` credentials file - keep it out of version control (it's a secret).
4. Open the target Google Sheet in your browser, click **Share**, and share it with the
   service account's email address (looks like
   `something@your-project.iam.gserviceaccount.com`, found on the service account's
   details page) with **Editor** access. The sheet won't be writable by the app without
   this step.
5. Copy the sheet's ID out of its URL:
   `https://docs.google.com/spreadsheets/d/`**`THE_SHEET_ID`**`/edit`.
6. In `.env`, set:
   ```
   GOOGLE_CREDS_JSON={"type":"service_account","project_id":"...", ...}
   GOOGLE_SHEET_ID=THE_SHEET_ID
   ```
   `GOOGLE_CREDS_JSON` is the full JSON key's contents as a single-line string (e.g.
   `GOOGLE_CREDS_JSON=$(cat your-service-account-key.json | jq -c .)`), parsed via
   `json.loads` - there's no credentials-file-on-disk path anymore, since Vercel's deployed
   function doesn't have a repo-local `credentials/` folder available. Rows are appended to
   the first worksheet (`sheet1`) of that spreadsheet.

This integration is optional: if either env var is unset, lead capture and the email
forward still work exactly as before - `sheets_service.py` logs a warning and skips the
Sheets append rather than raising, so a missing/misconfigured Sheets setup can never break
the chat flow or the email forward.

## Deployment

This app deploys to Vercel as a single Python Serverless Function (Vercel's
[Python runtime](https://vercel.com/docs/functions/runtimes/python) auto-detects the
`app` instance in `app/main.py` - no Mangum or other ASGI adapter needed, and no
`builds`/`routes` config; `vercel.json` here only sets `maxDuration`). Static widget files
are served straight from Vercel's CDN out of `public/` (see [The chat widget](#the-chat-widget)),
bypassing the Python function entirely.

**One-time setup, before the first deploy:**

1. Provision a Postgres database (e.g. [Supabase](https://supabase.com) or
   [Neon](https://neon.tech) free tier) and get its connection string.
2. Run `DATABASE_URL=<your postgres URL> python -m app.database` once, locally, to create
   the tables. This is deliberate manual step, not automatic - see [Database](#database).
3. In the Vercel project's dashboard, set the environment variables from `.env.example`:
   `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `RESEND_API_KEY`, `TEAM_EMAIL`, `DATABASE_URL`
   (the Postgres URL from step 1), `GOOGLE_CREDS_JSON`, `GOOGLE_SHEET_ID`, `CORS_ORIGINS`.
   **Never set `TEST_MODE` here** - see `TESTING.md`.
4. `.python-version` pins Python 3.12 (Vercel's supported versions are 3.12/3.13/3.14) -
   update it if you need a newer one.

**Test locally with the Vercel CLI before pushing:**

```bash
npm i -g vercel   # if not already installed
vercel dev
```

This runs the same Python runtime Vercel uses in production, including serving `public/`
from the site root the same way. Confirm `/`, `/chat`, and `/widget.js` all resolve
correctly before deploying.

## Testing

```bash
python tests/test_e2e.py
```

Runs one message through each intent (FAQ, recommend, escalate, off-topic, and a full
multi-turn lead capture) against the real orchestrator and agents — no mocking, so it
does make live Groq calls. Confirms:
- each intent routes to the right specialist agent and gets logged to `ChatHistory` with
  the correct `intent` value
- the off-topic message is refused by the guardrail *before* any specialist agent or
  `ChatHistory` write happens
- the lead flow correctly persists to the `Leads` table across turns
- blank/oversized messages are rejected with 422
- no response body contains anything resembling an API key or stack trace

Uses a throwaway SQLite file (`tests/_e2e_test.db`), cleaned up automatically. There's no
`pytest` in `requirements.txt` yet — this is a plain script with asserts and a pass/fail
summary; add `pytest` if the test suite grows past this smoke test.

The same file also has a mocked regression suite that doesn't call Groq at all — useful
for iterating on guardrail/routing logic without burning API quota. In addition to the
guardrail/routing/feedback regressions, it covers:
- `_feature_lead_session_db_persistence`: a lead form's partial state survives a simulated
  server restart (the in-memory session cache is cleared mid-flow, then the same session
  resumes correctly from the persisted `lead_sessions` row).
- `_feature_session_isolation_concurrent_leads`: two lead flows under different
  `session_id`s, with turns interleaved rather than run back-to-back, never cross-
  contaminate each other's in-memory or persisted state.
- `_feature_sheets_and_email_forward_failure_isolation`: a Google Sheets append failure
  never stops the email forward (or unsets `lead.forwarded`), and an email failure never
  stops the Sheets append - checked in both directions against real `Leads` rows.

```bash
python tests/test_e2e.py --mocked
```

### Pre-deploy gate: `tests/test_chatbot_flows.py`

```bash
python tests/test_chatbot_flows.py
```

Fully mocked (no live Groq/Resend/Sheets calls), so it's fast and deterministic enough
to run before every deploy - wire it into CI as one command, same as `test_e2e.py
--mocked`. Covers, end-to-end through `/chat` and `/feedback/*` with both reply content
*and* DB state asserted for each: the greeting, every widget quick-reply button (see
`public/widget.js`'s `QUICK_REPLIES`), the FAQ/recommend/escalate workers, a full lead
form from trigger to the `Leads` row + forwarding calls, mid-form cancellation,
self-recall (bare name and an explicit "show my info" ask), the off-topic guardrail, the
feedback card (all three faces, a reason chip, and cancel), the feedback free-text
fallback, cross-session isolation, state surviving a simulated restart (both lead
progress and, since [SESSION_STATE.md](SESSION_STATE.md)'s consolidation, the feedback
ask-latch too), and a defensive check that a leaked AI reasoning trace (a raw
`<think>...</think>` block) never reaches a user-facing reply - see
`app/services/ai_service.py`'s `_strip_reasoning_leak`.

## AI provider fallback

`app/services/ai_service.py`'s `get_ai_response()` (the only entry point every agent
calls — `intent_agent`, `faq_agent`, `recommend_agent`, `lead_agent`) tries Groq first
and, only if that single call fails (timeout, rate limit, connection error, non-2xx,
empty response), makes exactly one fallback attempt against OpenRouter
(`OPENROUTER_API_KEY` in `.env`, model configurable via `OPENROUTER_MODEL`, defaults to
`openai/gpt-oss-20b:free` — meta-llama's free Llama endpoints were pulled from
OpenRouter's catalog, so double-check `openrouter.ai/models` before changing this to
another `:free` model). No retry loop on either provider, so a genuinely down AI layer
fails fast rather than hammering OpenRouter's free-tier 20 req/min cap. Every call logs
which provider actually served the response (`served_by=groq` / `served_by=openrouter`)
— useful for spotting how often the fallback is triggering. If OpenRouter also fails,
`get_ai_response()` raises `AIServiceError` exactly as it always did with Groq alone,
so each call site's existing keyword-matched/heuristic fallback (unchanged) is still the
last resort.

## Security notes

- **No secrets/stack traces in responses**: `app/main.py` registers a catch-all exception
  handler that logs full details server-side and returns a generic message to the client.
  Every place that calls `ai_service` also catches `AIServiceError` locally and falls back
  to a safe message, so raw provider errors never reach `/chat` responses.
- **Input sanitization**: `sanitize_input()` in `database.py` (strips control chars, caps
  length) is applied to every user-supplied value before it's persisted — chat messages/
  responses in `save_chat_history`, and every lead field in `lead_agent.py` before it's
  written to the `Leads` table.
- **`.env` is gitignored** (along with `*.db`, `venv/`) double-checked
  no API keys are hardcoded anywhere in tracked files.
