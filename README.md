# XQORA Chatbot

AI customer support chatbot for theXQORA Technologies website. It answers questions about XQORA's services, recommends the right offering, collects leads, escalates complex queries to the team, and
collects feedback reducing manual support load and improving lead quality.

Built with FastAPI and a lightweight JavaScript widget, using a multi-agent
architecture: one orchestrator classifies intent and routes to a dedicated agent for
FAQs, recommendations, lead collection, escalation, or feedback.

## How it works

Every `/chat` request goes through a single decision point, `app/orchestrator.py`:

1. **Feedback check** — if the session was just asked for feedback, the reply is parsed
   for a rating/comment (see [Feedback](#feedback)) before anything else happens.
2. **Closing-phrase / natural-close check** — a sign-off ("thanks", "bye"), a just-finished
   lead submission, or an escalation all trigger a casual feedback ask.
3. **Lead-flow check** — if the session is mid-way through lead collection, the message is
   routed straight back into `lead_agent.py` instead of being reclassified.
4. **Guardrail + intent classification** — `intent_agent.py` runs deterministic pre-checks
   (near-empty input, greetings, bare category words like "pricing", self-identity
   questions, a hard off-topic keyword/pattern filter, a hard escalate-signal filter) before
   ever calling the AI classifier, then labels the message `faq`, `recommend`, `lead`,
   `escalate`, or `off_topic`.
5. **Specialist agent dispatch** — the matching agent (`faq_agent.py`, `recommend_agent.py`,
   `lead_agent.py`, or `escalation_agent.py`) generates the reply, grounded in
   `data/faq.json` / `data/services.json` where applicable.
6. **Logging** — the turn is saved to `ChatHistory` (skipped for greetings/off-topic
   refusals) so the next message's classification and specialist replies can use recent
   conversation context.

## Setup

```bash
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env          # fill in your Groq API key, Resend key, and team email
uvicorn app.main:app --reload
```

Visit `http://127.0.0.1:8000` — should return a health check response.
Visit `http://127.0.0.1:8000/docs` for interactive API docs (auto-generated by FastAPI).

## The chat widget

`static/widget.js` is a single self-contained script — no external framework or CSS
library, so it works standalone when dropped into any page.

**Drop-in usage** (on the real XQORA site, pointing at wherever the API is deployed):

```html
<script src="https://YOUR_API_HOST/static/widget.js" data-api-url="https://YOUR_API_HOST/chat"></script>
```

- `data-api-url` is optional. If omitted, the widget POSTs to `/chat` on the page's own
  origin — which is exactly what happens in local testing, since `static/test.html` is
  served by this same FastAPI app via the `/static` mount.
- To test locally: run the server, then visit `http://127.0.0.1:8000/static/test.html`.
  The bubble should appear fixed to the bottom-right corner; clicking it opens the panel.

**session_id behavior**: the widget generates one `session_id` per page load
(`crypto.randomUUID()`, with a fallback for older browsers) and keeps it in a JS variable
only — not `localStorage` or a cookie. Refreshing the page starts a new session. The
backend also accepts and honors a client-supplied `session_id` on `/chat`, so this is a
widget-side choice, not a backend constraint — swap in persistent storage in `widget.js`
later if cross-refresh continuity is wanted.

**Restyling**: all colors/radii/shadows live in the `THEME` object at the top of
`widget.js`:

| Key | Value | Used for |
|---|---|---|
| `teal` | `#14b8a6` | bubble background, user message bubbles, send button, input focus ring |
| `tealDark` | `#0d9488` | send button hover |
| `navy` | `#0a1e3f` | chat panel header background |
| `textDark` | `#0f172a` | bot message text |
| `panelBg` | `#f8fafc` | chat panel body background |
| `white` | `#ffffff` | header text, bubble icon, input background |
| `radius` / `radiusSm` | `14px` / `10px` | panel corners / message bubble & input corners |
| `shadow` / `bubbleShadow` | — | panel drop shadow / bubble glow |

Nothing else in the file needs to change to reskin the widget — markup, layout, and the
`/chat` wiring are independent of `THEME`.

## CORS

`CORS_ORIGINS` in `.env` controls which origins may call `/chat` from a browser (the
widget relies on this). **The default in `app/core/config.py` is a placeholder**
(`https://xqora.com,https://www.xqora.com`) — replace it with the real production
domain(s) before deploying:

```
CORS_ORIGINS=https://xqora.com,https://www.xqora.com
```

Comma-separated for multiple domains (e.g. staging + production). Never set this to `*`
in production — that would let any website embed the widget and call this API.

## Feedback

After a conversation reaches a natural close point — a lead gets submitted, an escalation
happens, or the user signs off with something like "thanks" or "bye" — `feedback_agent.py`
casually asks for a quick rating/comment (e.g. "Before you go, how'd this chat go? (1-5,
or just tell me)"). This only fires once per session:

- A reply starting with a number 1-5, or containing a recognized rating word (e.g.
  "great", "poor"), is saved to the `Feedback` table (`session_id`, `rating`, `comments`,
  `date`) and the session is marked as given.
- Anything else — ignored, or the user just moves on to another question — marks the
  session as declined. The ask is never repeated, and the message that declined it is
  still processed normally (not swallowed).
- Detection is deterministic (regex/keyword-based), not AI-based, so a feedback reply can
  never be misclassified as off-topic or misrouted to another agent.

## Testing

```bash
python tests/test_e2e.py
```

Runs one message through each intent (FAQ, recommend, escalate, off-topic, and a full
multi-turn lead capture) against the real orchestrator and agents — no mocking, so it
does make live Groq calls. Confirms:
- each intent routes to the right specialist agent and gets logged to `ChatHistory` with
  the correct `intent` value
- the off-topic message is refused by the guardrail *before* any specialist agent or
  `ChatHistory` write happens
- the lead flow correctly persists to the `Leads` table across turns
- blank/oversized messages are rejected with 422
- no response body contains anything resembling an API key or stack trace

Uses a throwaway SQLite file (`tests/_e2e_test.db`), cleaned up automatically. There's no
`pytest` in `requirements.txt` yet — this is a plain script with asserts and a pass/fail
summary; add `pytest` if the test suite grows past this smoke test.

The same file also has a mocked regression suite that doesn't call Groq at all — useful
for iterating on guardrail/routing logic without burning API quota:

```bash
python tests/test_e2e.py --mocked
```

## Security notes

- **No secrets/stack traces in responses**: `app/main.py` registers a catch-all exception
  handler that logs full details server-side and returns a generic message to the client.
  Every place that calls `ai_service` also catches `AIServiceError` locally and falls back
  to a safe message, so raw provider errors never reach `/chat` responses.
- **Input sanitization**: `sanitize_input()` in `database.py` (strips control chars, caps
  length) is applied to every user-supplied value before it's persisted — chat messages/
  responses in `save_chat_history`, and every lead field in `lead_agent.py` before it's
  written to the `Leads` table.
- **`.env` is gitignored** (along with `*.db`, `venv/`) double-checked
  no API keys are hardcoded anywhere in tracked files.
